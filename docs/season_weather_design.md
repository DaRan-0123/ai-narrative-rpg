# 季节/天气动态判断设计方案

> 对应 TODO.md 第 2 项"季节/天气判断"。2026-07-28 设计并经用户批准，本文档为施工依据。
> 依据：src/game_state.py、src/prompts.py、src/ui/game_window.py 现状（P3 每轮跑事实提取；P1 的 game_season/game_time 由 P1 自由填写，无连续机制）。

---

## 一、现状与问题

| 现有机制 | 局限 |
|---|---|
| P1 输出 `game_season` / `game_time`（可选字段） | 完全由 P1 每轮自由发挥，没有累积概念：第 3 轮春天、第 50 轮还是春天 |
| `weather_environment` 由 P1 填写 | 天气同样无连续性约束，可能上一秒暴雨下一秒晴天 |
| 无游戏内日历 | "过了几天"无从谈起，季节更替永远不会发生 |

**后果**：长线游戏（几十上百轮）里世界时间是静止的，季节/天气只是随机装饰。

## 二、设计目标

1. 游戏内有**日历**：每轮消耗的时间可累积，季节由日历确定，不再靠 P1 自由判断
2. 天气**默认连续**，只有叙事明确描写变化时才允许改变
3. 零新增 API 调用类型（复用每轮必跑的 P3），token 成本可忽略
4. v1 尽量简单：正常速度流逝，不做加速机制（用户明确不要）

## 三、骨架：游戏内日历

- `player_state` 新增 `game_day`：**浮点**，游戏内累计天数，从 1 开始
- **默认历法**：一年 4 季 × 30 天 = 360 天（春 1-30 / 夏 31-60 / 秋 61-90 / 冬 91-120 / 春 121-150 ……）
- **自定义历法留接口**：`world_template.calendar = {"seasons": [{"name": "...", "days": N}, ...]}`，
  `get_season_for_day(game_day, calendar)` 已支持；创建世界流程（P9/P10）本期不接，后续扩展
- **季节由日历确定**：`game_window` 在每轮 P1 返回后用日历季节覆盖 `player_state.game_season`，
  P1 自己的季节判断不再生效；P1 prompt 注入正确季节让它叙事自洽
- **旧存档初始化（向后兼容，对批准方案的细化）**：约束要求"旧存档无 game_day 时初始化为 1"，
  但旧存档已有 `game_season`（如"深秋"），机械置 1 会让季节从深秋跳回春季、破坏叙事连续性。
  因此实现为：**若旧存档已有 game_season，则对齐到该季节的第一天**（春→1、夏→31、秋→61、冬→91），
  否则初始化为 1。新存档无 game_season 时即为 1，符合原约束。

## 四、判断：P3 每轮输出扩展

P3（事实提取，flash，temp=0.3，本来就每轮跑）输出从纯 facts 数组扩展为 JSON 对象：

```json
{
  "facts": [ {"content": "...", "confidence": "high", "source": "..."} ],
  "time_passed": "约2小时",
  "weather": {"current": "小雪转晴", "changed": true, "reason": "叙事提到风停了"},
  "season_sign": "无"
}
```

- **time_passed**：P3 估算本轮经过的游戏时间。代码解析累加进 game_day（解析规则见第五节）
- **weather**：把上一轮天气传给 P3，prompt 约束**默认延续（changed=false），叙事有明确依据才允许 changed=true**，reason 必须引用叙事依据。changed=true 且有 current 时写回 `player_state.weather_environment`
- **season_sign（v1 简化）**：只记录不改变——作为一条普通 fact（"季节迹象：……"）存入 known_facts，
  随全量事实注入 P1 作为参考，**不改变日历驱动的季节**。为后续"迹象修正历法"留数据

**向后兼容**：P3 返回旧的纯数组格式、或缺新字段时，流程不崩；time_passed 缺失按解析失败处理（兜底 0.25 天，保证日历持续走动）。

## 五、time_passed 解析规则（纯函数 `parse_time_passed`）

| 输入示例 | 解析结果（天） | 规则 |
|---|---|---|
| "睡到第二天" / "次日" | 1.0 | 优先匹配"第二天/次日/翌日" |
| "半天" | 0.5 | 字面匹配（须在 N天 规则之前，"半"不是数字） |
| "走了三天" / "两天" | 3.0 / 2.0 | 中文数字或阿拉伯数字 + 天 |
| "一夜" / "一晚" / "通宵" | 0.5 | 夜间按半天计 |
| "约2小时" / "三个小时" | 2/24 ≈ 0.083 / 0.125 | N小时 ÷ 24 |
| "两刻钟" | 2×0.25÷24 ≈ 0.021 | 1 刻钟 = 0.25 小时 |
| "半小时" | 0.5÷24 ≈ 0.021 | 字面"半"+"小时" |
| "四十分钟" | 40÷60÷24 ≈ 0.028 | 分钟 ÷ 60 ÷ 24 |
| 无法解析 / 缺失 | **0.25（兜底）** | 保证每轮至少推进约 6 小时 |

匹配顺序：第二天/次日 → 半天 → N天 → 夜 → 半小时 → N小时 → 刻钟 → 分钟 → 兜底。
中文数字支持 一二两三四五六七八九十 与阿拉伯数字。

## 六、闭环：注入 P1

P1 prompt 新增【当前时节】块：

```
【当前时节】
- 游戏内日期: 第61天（秋季）
- 当前天气: 中雨持续
- 要求: 天气与季节应保持连续，除非剧情明确推进时间或改变天气
```

**块位置选择（缓存优化，依据 HANDOVER 4.7）**：放在【当前区域】之后、【玩家当前状态】之前。理由：
- P1 前缀缓存要求"固定内容在前、易变内容在后"
- 【当前时节】的变化频率低：整数天数几天才变一次、天气只在 P3 判定 changed=true 时变
- 其后的【玩家当前状态】【在场NPC档案】【最近对话历史】【当前轮次】【玩家输入】都是**每轮必变**的块，
  时节块放在它们之前可最大化前缀缓存命中；若并入固定的【当前区域】块内反而会污染这个全固定块

## 七、实施改动清单

| 文件 | 改动 |
|---|---|
| `src/prompts.py` | P3_SYSTEM/build_p3_user 扩展（对象输出+天气连续性约束，build_p3_user 增加 current_weather 参数）；build_p1_user 加【当前时节】块 |
| `src/game_state.py` | `parse_time_passed`（纯函数）、`get_season_for_day`（纯函数，含自定义历法接口）、`get_game_day`（含旧存档对齐初始化）、`add_game_days`、`get_season`、`get_date_display` |
| `src/ui/game_window.py` | P1 返回后用日历季节覆盖 game_season；`_call_p3_async` 扩展解析（数组/对象双格式兼容、time_passed 累加、weather 写回、season_sign 存 fact） |

无新增 API 调用类型；成本 = P3 输出增量约 40-60 token/轮。

## 八、验证方式

1. 单测：time_passed 解析表全量用例、季节计算边界（day1春/day31夏/day91冬/day121春）、P3 旧数组格式兼容
2. 真实调用（saves/老陈的旅途）：含明确天气变化的假叙事 → changed=true 且写回；无天气变化的假叙事 → changed=false 延续
3. P1【当前时节】块内容检查

## 九、明确不做的（v1 简化）

- **不做加速机制**：用户明确不要；正常速度流逝（每轮 0.083-1 天）
- **season_sign 不改变季节**：只记录为 fact 供 P1 参考；积累足够数据后再做"迹象修正历法"
- **不接自定义历法到创建流程**：`world_template.calendar` 接口已留，P9/P10 后续接
- **不做天气对玩法的数值影响**（如雨天行动惩罚）：只影响叙事连续性

## 十、后续扩展点

1. P9/P10 创建世界时生成自定义历法（seasons 数组）
2. season_sign 积累后做历法修正（如连续 5 条"落叶"迹象提示实际已入秋）
3. game_time（清晨/正午/深夜）同样纳入日历：time_passed 的小数部分驱动时段
4. 天气对叙事的反向约束（P1 长雨天提示室内剧情）
